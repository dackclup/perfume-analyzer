## สรุปย่อ

- **หลักใหญ่: ทำให้ AI ตัวเดียวทำงานได้น่าเชื่อถือก่อน แล้วค่อยให้หลายตัวทำพร้อมกัน** ถ้ายังเชื่อใจไม่ได้ การเพิ่มจำนวน AI แค่ผลิตงานที่ไม่ได้ตรวจเร็วขึ้น [ต้นฉบับ]
- **"เสร็จ" ต้องมีหลักฐานจากของจริง** ไม่ใช่คำยืนยันของ AI ตรวจไม่ได้ให้เขียนว่า "ยังสรุปไม่ได้" ไม่ใช่ "ผ่าน" [ต้นฉบับ]
- **ความผิดพลาดที่เกิดซ้ำ 2 ครั้ง ต้องย้ายไปเป็นระบบตรวจ** ไม่ใช่เขียนกำชับเพิ่ม เพราะกฎที่เป็นข้อความ AI ข้ามได้โดยไม่มีอะไรล้ม [ต้นฉบับ]
- **ผู้ตรวจต้องไม่ใช่ผู้ทำ** และควรต่างมุมมองกัน [ต้นฉบับ]
- **AI จำอะไรข้ามแชทไม่ได้ ความรู้ต้องอยู่ในไฟล์** จบงานให้สรุปบทเรียน · คำถามที่ทดลองหรือค้นหาคำตอบได้ให้ AI หาเอง ถามคนเฉพาะเรื่องรสนิยม [ต้นฉบับ]
- **โปรเจกต์นี้ทำบางส่วนแล้ว** (ตรวจด้วย GitHub Actions และผู้ตรวจอิสระในรอบ 4–5) แต่มีจุดที่ข้ามขั้น คือหลายแชทแก้เอกสารพร้อมกันโดยไม่แบ่งงาน ไฟล์นี้รวมทุกอย่างเป็น **กติกา 16 ข้อ (ส่วน 4)** และ **ตารางกฎคู่กับสิ่งที่บังคับ (ส่วน 3.2)** · **รอบ 7:** แถว 1, 2, 4, 5, 7 มีเช็กที่ล้มได้จริงแล้ว รันครั้งแรกพบเรื่องที่ต้องแก้ 6 เรื่องในเอกสารที่ผ่านการตรวจมาแล้ว และผู้ตรวจอิสระพบช่องโหว่ของตัวตรวจเอง 10 ข้อ (แก้แล้ว) [โปรเจกต์นี้]

## 1. Lauren Tan คือใคร

- ใช้ชื่อ **poteto** (X: @poteto) · README ของ pstack บอกว่าเคยทำงานกับโค้ดหลายล้านบรรทัดที่ Meta, Netflix และ Cursor และอยู่ในทีม React core ช่วยดูแล React Compiler [ต้นฉบับ]
- ปัจจุบันทำ Grok Bot และ Cursor ที่ SpaceXAI (จากโปรไฟล์ LinkedIn ของเธอ ตรวจ 14 ต.ค. 2026)
- **pstack** คือชุด skill ที่เธอบอกว่าใช้ทุกวัน ปล่อยเป็นปลั๊กอินของ Cursor แบบ MIT (เวอร์ชัน 0.15.23) มีทางเข้าหลักคือ `/poteto-mode` ซึ่งเลือก playbook ให้จาก 23 แบบ และมีหลักการสั้นๆ 24 ข้อ [ต้นฉบับ]
- pstack ทำมาสำหรับ Cursor · มีคนในชุมชนพอร์ตไปใช้กับ Claude Code และ Codex (เช่น pstack-claude) แต่ไม่ได้ทำโดยเธอ (จากข่าวแหล่งรอง)
- คำขวัญของ pstack คือ "if you want to go fast, go deep first" เป้าหมายคือเขียนโค้ดน้อยลงแต่คุณภาพสูงขึ้น ไม่ใช่เขียนให้ได้มากที่สุด [ต้นฉบับ]
- **ทอล์กเรื่องสร้างความเชื่อใจก่อนรัน AI หลายตัวพร้อมกัน** ราว 38 นาที เดิมจะพูดที่งาน Cursor Compile London แล้วย้ายไปไลฟ์ · ไม่มีชื่อทอล์กทางการในแหล่งที่หาได้ บทความสรุปตั้งชื่อว่า "Trust First, Then Parallel" [สรุปทอล์ก]
- **ตัวเลขที่เธอรายงานเอง ยังไม่มีใครตรวจ:** ทีมวิศวกรใช้ skill เหล่านี้ราว 10,000 ครั้งในสัปดาห์เดียว (จากโพสต์ X ของเธอ) · PR ราว 2,000–2,500 ต่อเดือน (ทอล์กกับหัวข้อโพสต์ให้ตัวเลขไม่ตรงกัน) [สรุปทอล์ก]

## 2. วิธีทำงานของเธอ 12 ข้อ

**2.1 เชื่อใจก่อน แล้วค่อยขนาน** [ต้นฉบับ: คู่มือบท 7]
ก่อนปล่อย AI ทำงานเองหรือรันหลายตัวพร้อมกัน ต้องครบ 4 ข้อ:
1. เคยทำงานนั้นเอง หรือเคยดู AI ทำแล้ว จึงรู้ว่างานดีหน้าตาเป็นยังไง
2. AI มีเครื่องมือเดียวกับที่เราใช้ตรวจเอง
3. ทุกขั้นพิสูจน์งานตัวเองได้ และหยุดสายพานได้ถ้างานไม่ถึงเกณฑ์
4. อ่านบันทึกการทำงานแล้ว และเปลี่ยนความผิดพลาดที่เกิดซ้ำเป็นเครื่องมือหรือเช็กแล้ว

ในทอล์กเธออธิบายว่า AI จะลอกแบบสิ่งที่มีอยู่แล้วในงาน งานที่มีแบบผิดๆ ค้างอยู่ จึงยิ่งผิดซ้ำเมื่อมี AI หลายตัว และเปรียบตัวเองเป็นเชฟร้านมิชลิน ไม่ใช่เจ้าของโรงงาน คนยังต้องรับผิดชอบทุกงานที่ออกไป [สรุปทอล์ก]

**2.2 พิสูจน์ว่าใช้ได้จริง (Prove It Works)** [ต้นฉบับ]
- ตรวจของจริง: รันจริง อ่านค่าจริง ดูไฟล์จริง ไม่ใช่ดูจากตัวแทนหรือคำรายงานของ AI
- ถ้าเขียนเป็นสคริปต์ที่รันซ้ำได้ ดีที่สุด คนตรวจรันเองได้แทนการเชื่อคำพูด
- ทุกข้อความต้องมีหลักฐานหรือป้ายในประโยคเดียวกัน: **วัดแล้ว / อนุมาน / เดา**
- ตรวจไม่ได้ให้บอกว่า "inconclusive" (ยังสรุปไม่ได้) ไม่ใช่ผ่าน

**2.3 สั่งงานด้วย 5 อย่าง** [ต้นฉบับ: คู่มือบท 2 และ 7]
เป้าหมาย · เงื่อนไขว่าเสร็จที่ตัดสินได้ว่าผ่าน/ไม่ผ่าน · หลักฐานที่อยากเห็น · สิ่งที่รู้อยู่แล้ว · ข้อจำกัดจริง
- อย่าบอกวิธีทำทีละขั้น และอย่าเดาสาเหตุให้ก่อน เพราะ AI จะค้นแค่ตรงที่ชี้
- งานที่โจทย์ยังกำกวม ให้ AI **สรุปปัญหาด้วยคำของตัวเองก่อน** ยังไม่ต้องลงมือ
- "ทำไปสัก 4 ชั่วโมง" ไม่ใช่เงื่อนไขว่าเสร็จ
- ถ้าต้องแก้ทิศกลางทาง ให้ **เอ่ยชื่อหลักการ** (เช่น "Prove It Works") แทนการอธิบายยาว เพราะ AI อ่านกฎเต็มไว้แล้ว ชื่อเดียวจึงแก้ได้แม่นกว่า [สรุปทอล์ก]

**2.4 แก้ที่ระบบ ไม่ใช่กำชับซ้ำ (`/correct`)** [ต้นฉบับ]
ความผิดพลาดหนึ่งแบบนับเป็น "แบบ" เมื่อเกิด 2 ครั้ง แล้วแก้ที่ระดับสูงสุดที่ทำได้:
1. ออกแบบให้ผิดไม่ได้ (มีแหล่งความจริงเดียว ลบทางเก่าที่ AI จะลอก)
2. ให้ระบบตรวจล้มเมื่อผิด และข้อความแจ้งบอกวิธีแก้
3. มีชุดทดสอบจับ
4. เขียนเป็นกฎ — ระดับต่ำสุด ใช้กับเรื่องที่ต้องใช้วิจารณญาณเท่านั้น

และเก็บ **ตารางคู่กฎกับสิ่งที่บังคับใช้** ไว้ ถ้ากฎไหนไม่มีอะไรบังคับแล้วผิดซ้ำ ให้ยกระดับทันที

**2.5 สร้างเครื่องมือ (Build the Lever)** [ต้นฉบับ]
งานที่ไม่ใช่เรื่องเล็ก ให้เขียนสคริปต์ที่ทำหรือพิสูจน์งาน แทนการทำมือ · ทำหน่วยแรกด้วยมือเพื่อเรียนสูตร แล้วค่อยเขียนเครื่องมือ · สคริปต์ตัวเดียวที่ทำครบทุกหน่วย ดีกว่าแจกงานให้ AI หลายตัวทำมือ

**2.6 ผู้ตรวจอิสระและหลายมุมมอง** [ต้นฉบับ]
- ให้ AI จากหลายตระกูลโมเดลตรวจงานแยกกัน แล้วคัดว่าข้อไหนต้องแก้ ข้อไหนทิ้งพร้อมเหตุผล — ไม่แก้ตามทุกข้อ
- AI ที่ตัดสินว่างานผ่าน ต้องไม่ใช่ตัวที่ทำงานนั้น
- งานใหม่ให้ AI ตัวใหม่ที่ได้รับสรุปงานครบ ดีกว่าสั่งตัวเดิมต่อ เพราะคำสั่งหายระหว่างทางได้

**2.7 บันทึกการตัดสินใจ (`/show-me-your-work`)** [ต้นฉบับ]
งานยาวหรืองานที่ปล่อยให้ AI ทำเอง ให้บันทึกบรรทัดละหนึ่งการตัดสินใจ: เวลา · ขั้น · ทำอะไร · ทำไม · หลักฐาน (ลิงก์หรือไฟล์ ไม่ใช่ย่อหน้า) · ผล · กลับมาแล้วอ่านส่วน "ควรดูให้ดี" ก่อน
งานที่ปล่อยให้ทำเองนาน ให้ทำทีละรอบ: **หนึ่งการเปลี่ยน + หนึ่งการตรวจ + หนึ่งบรรทัดบันทึก** [ต้นฉบับ: คู่มือบท 7]

**2.8 การแบ่งงานและการขออนุญาต** [ต้นฉบับ]
- อ่านข้อมูลปริมาณมากผ่าน AI ผู้ช่วยหรือสคริปต์ เก็บแค่สรุปไว้ในแชทหลัก
- งานที่ย้อนได้ ทำเลยแล้วรายงาน · งานที่ย้อนไม่ได้ (ลบข้อมูล ส่งข้อความถึงลูกค้า ปล่อยของขึ้นระบบจริง) ต้องหยุดถาม
- AI หลายตัวทำงานพร้อมกัน ต้องมีพื้นที่ของตัวเอง ห้ามใช้ที่เดียวกัน ไม่อย่างนั้นเขียนทับกัน

**2.9 คนดูแลสวน (gardener)** [สรุปทอล์ก + ต้นฉบับ]
ระบบตรวจกับเอกสารจะค่อยๆ ไม่ตรงกับของจริง ต้องมีรอบตรวจซ้ำประจำ และต้องคอยกำจัดข้อมูลผิดหรือแบบเก่า เพราะ AI จะลอกต่อ · pstack แนะนำให้ดูแลระบบตรวจอย่างน้อยวันละครั้งด้วยงานตั้งเวลา (ของโปรเจกต์นี้ไม่ต้องถี่ขนาดนั้น)

**2.10 ความจำอยู่ในไฟล์ ไม่ใช่ในแชท** [ต้นฉบับ: repo brainmaxxing และ noodle + สรุปทอล์ก]
- เธอเปรียบ AI เหมือนพนักงานใหม่ที่ความจำเสื่อมตลอดเวลา ทางแก้คือกฎ skill เครื่องมือ และความจำที่เขียนลงไฟล์ ไม่ใช่ prompt ที่ยาวขึ้น [สรุปทอล์ก]
- ไฟล์กฎสั้นและเป็นข้อๆ ให้อ่านก่อนเริ่มงาน และเขียนเพิ่มหลังพลาดหรือถูกแก้ · เก็บหนึ่งหัวข้อต่อหนึ่งไฟล์ [ต้นฉบับ: noodle]
- **reflect**: สรุปบทเรียนหลังจบงาน · README ของเธอบอกว่าขั้นนี้ขั้นเดียวให้คุณค่าส่วนใหญ่แล้ว · **meditate**: ทบทวนแล้วตัดเนื้อหาที่ล้าสมัยออกเป็นระยะ [ต้นฉบับ: brainmaxxing]
- มี "แผนที่" ว่าอะไรอยู่ตรงไหน พิสูจน์ด้วยอะไร และมีกับดักอะไร (ของโปรเจกต์นี้คือตาราง 3.3)

**2.11 วางแผนด้วยการทดลอง และแก้ให้น้อยที่สุด** [ต้นฉบับ]
- README ของ pstack บอกว่าเธอไม่เชื่อการวางแผนบนกระดาษ สเปกที่ดีที่สุดคือของจริง → ทำต้นแบบเล็กๆ แทนการเขียนแผนยาว
- ถ้าทดลองหรือค้นแล้วรู้คำตอบได้ ให้ผลทดลองตัดสิน · เก็บคำถามที่ต้องถามคนไว้เฉพาะเรื่องรสนิยม [ต้นฉบับ: poteto-mode, never-block-on-the-human]
- **Laziness Protocol**: เลือกการเปลี่ยนแปลงที่เล็กที่สุดที่แก้ปัญหาได้ ลบหรือรวมของเก่าก่อนเพิ่มของใหม่
- แบ่งงานเป็นหน่วยเล็กที่แต่ละหน่วยจบด้วยการตรวจ (Sequence Work into Verifiable Units)

**2.12 ทดสอบกฎเหมือนทดสอบโค้ด (evals)** [สรุปทอล์ก]
- เธอทดสอบ skill ด้วยการให้ AI หลายตัวทำโจทย์เดียวกัน ตั้งเกณฑ์ให้คะแนน แล้วใช้โมเดลอื่นเป็นผู้ตัดสินเพื่อลดอคติ

## 4. กติกาสำหรับ AI ในโปรเจกต์นี้ (16 ข้อ)

**แหล่งความจริง**
1. รายชื่อ รหัส ลิงก์สินค้า = ไฟล์ 7 · เพดาน IFRA = ไฟล์ 1 · สารห้าม = ไฟล์ 0 / ไฟล์ 4 ส่วน O · ถ้าข้อมูลซ้ำหลายไฟล์ แก้ที่แหล่งความจริงก่อน แล้วไฟล์อื่นอ้างถึง
2. ห้ามสรุปว่า **"ร้านไม่มี"** จนกว่าจะค้นไฟล์ 7 **และ sitemap ทั้งร้าน** แล้ว (ไฟล์ 7 มีเฉพาะหมวดน้ำหอม) · ห้ามสรุปว่า **"ร้านมี"** สำหรับรหัสที่ติด ⓧ
3. ตัวเลข IFRA ใช้จากเอกสารมาตรฐาน IFRA เท่านั้น ระบุเลข STD หรือแหล่ง · ค่าจากหน้าผู้ขายใช้เป็นตัวเทียบได้ แต่ไม่ใช่ค่าที่บันทึก
4. ห้ามแนะนำสารในรายการห้าม แม้จะเป็นตัวแทนหรือเป็นส่วนผสมของสารอื่น (เช่น Verdantiol มี Lilial)
5. ลิงก์ร้านคัดลอกจากไฟล์ 7 เท่านั้น ห้ามพิมพ์ URL เอง · ตัวเลขในวงเล็บหลังชื่อวัตถุดิบหมายถึงรหัสสินค้าเสมอ เลขอื่นให้เขียนชื่อนำ เช่น (Annex II 359) · รหัสที่ไม่อยู่ใน sitemap เขียน ⓧ หลังรหัสทุกตัว เช่น (2890 ⓧ)

**หลักฐาน**
6. ทุกข้อเท็จจริงติดป้าย: **ยืนยันแล้ว (แหล่ง) / อนุมาน / เดา** · ราคาทุกตัวติด "ประมาณ (รอบแรก)"
7. งานจะ "เสร็จ" ต้องมีหลักฐานที่เปิดดูได้ (ลิงก์ ผลรันสคริปต์ ตาราง) · ตรวจไม่ได้ให้เขียน "ยังตรวจไม่ได้" พร้อมเหตุผล

**การแก้เอกสารและการทำงานพร้อมกัน**
8. อ่านเอกสารฉบับล่าสุดก่อนแก้ทุกครั้ง แก้เฉพาะจุด และห้ามเขียนทับด้วยสำเนาเก่า · ถ้าพบว่าแชทอื่นเพิ่งแก้ ให้รวมงานของเขาไว้ · ในแชท Claude Code: อ่านด้วย project_read → `pull_docs.py` → แก้ใน `project-docs/` → `docs_check.py` ต้องผ่าน → อ่านซ้ำก่อนเขียนกลับ → push สำเนาขึ้น repo (ขั้นตอนเต็ม รวมการรวม 3 ทางด้วย `safe_merge.py` อยู่ใน README ของ repo dackclup/perfume-analyzer · ถ้าขัดกัน ให้ทำตาม README)
9. ถ้าจะให้หลายแชททำพร้อมกัน แบ่งเจ้าของไฟล์ให้ชัดก่อนเริ่ม (เช่น แชท A ไฟล์ 1–4 · แชท B ไฟล์ 8–9 และ GitHub) · งานบน GitHub แยก branch ต่อแชท
10. ทุกรอบที่แก้ข้อมูล บันทึกในไฟล์ 8: วันที่ · ทำอะไร · ทำไม · หลักฐาน · ผล · จบรอบให้สรุป **บทเรียน 1–3 ข้อ** (reflect) ไว้ท้ายบันทึกเดียวกัน

**วิธีทำงาน**
11. งานใหญ่ (หลายไฟล์ หรือตรวจหลายร้อยรายการ) ใช้สคริปต์หรือ GitHub Actions ไม่ไล่มือ · งานที่แก้ข้อมูลความปลอดภัย (IFRA สารห้าม) ต้องมีผู้ตรวจอิสระที่ไม่ได้เป็นคนแก้ ตรวจก่อนบันทึก
12. งานที่ย้อนได้ (แก้เอกสาร เพิ่มไฟล์) ทำต่อได้เลยแล้วรายงาน · งานที่ย้อนไม่ได้ (ลบไฟล์หรือ branch, merge, สั่งซื้อ, ส่งข้อความ, เปิดสาธารณะ) ต้องถามก่อน · ถ้าเว็บปฏิเสธ (403, robots.txt) ให้หยุด ห้ามหาทางเลี่ยง
13. แก้ความผิดพลาดแบบเดิมเป็นครั้งที่ 2 → เพิ่มแถวในตาราง 3.2 และเสนอเช็กอัตโนมัติ ไม่ใช่แค่เพิ่มกฎข้อความ
14. แก้ให้เล็กที่สุดที่แก้ปัญหาได้ · ถ้ามีข้อมูลเก่าที่ซ้ำหรือผิด ให้รวมไปที่แหล่งความจริง หรือเสนอลบก่อนเพิ่มของใหม่ (การลบยังต้องถามตามข้อ 12)
15. คำถามที่ค้นหรือคำนวณหาคำตอบได้ ให้ AI หาเอง · ถามผู้ใช้เฉพาะเรื่องรสนิยม (เช่น ชอบกลิ่นแนวไหน) และงานที่ย้อนไม่ได้ (ข้อ 12) · ถ้าต้องถาม ให้ทำส่วนที่ทำได้ไปก่อน

**การปรับกติกา**
16. แก้กติกาในไฟล์นี้หรือ Project instructions เมื่อไหร่ ให้ทดสอบในแชทใหม่ด้วยคำถามตัวอย่าง 3–5 ข้อ (เช่น ถามสินค้าที่ร้านมีแต่หายาก · ขอสารตัวแทนที่อาจติดรายการห้าม · ขอราคา) ว่า AI ทำตามกติกาจริง · และตัดกฎที่ล้าสมัยหรือซ้ำออกในรอบเดียวกัน (meditate)

### 4.1 ข้อความสำหรับวางใน Project instructions

กฎในไฟล์ AI จะเห็นก็ต่อเมื่อเปิดอ่าน ข้อความสั้นนี้วางในคำสั่งประจำโปรเจกต์ (Project instructions) เพื่อให้ทุกแชทในโปรเจกต์ได้รับอัตโนมัติ · ผู้ใช้วางฉบับนี้แล้วเมื่อ 17 ต.ค. 2026 · ถ้าแก้ข้อความในบล็อกนี้ ต้องวางใหม่ใน Project instructions ในรอบเดียวกัน ไม่อย่างนั้นสองที่จะไม่ตรงกัน (ในแชท Claude Code เทียบได้จาก project_info):

```
โปรเจกต์ทำน้ำหอมฉีดตัวแนวดีไซน์เนอร์ วัตถุดิบจาก MySkinRecipes
งานที่ไม่ใช่คำถามสั้น ให้โหลดสกิล perfume-mode ก่อนเริ่ม แล้วทำตาม playbook จนจบ
ก่อนแก้เอกสาร อ่านไฟล์ 10 ส่วน 4 (กติกา 16 ข้อ) และอ่านไฟล์ฉบับล่าสุดก่อนเขียนทุกครั้ง
- รายชื่อ/รหัส/ลิงก์สินค้า ใช้ไฟล์ 7 เท่านั้น ห้ามบอกว่า "ร้านไม่มี" ก่อนค้นไฟล์ 7 และ sitemap ทั้งร้าน · รหัสติด ⓧ อาจเลิกขายแล้ว · เลขในวงเล็บหลังชื่อวัตถุดิบ = รหัสสินค้าเท่านั้น
- เพดาน IFRA ใช้ไฟล์ 1 (เอกสารมาตรฐาน) · ห้ามแนะนำสารในรายการห้าม (ไฟล์ 0, ไฟล์ 4 ส่วน O)
- ทุกข้อเท็จจริงติดป้าย ยืนยันแล้ว/อนุมาน/เดา · ราคาเป็นค่าประมาณ ต้องเช็กในตะกร้า
- "เสร็จ" ต้องมีหลักฐานที่เปิดดูได้ ตรวจไม่ได้ให้บอกตรงๆ
- ค้น/คำนวณเองก่อน ถามผู้ใช้เฉพาะเรื่องรสนิยมหรืองานที่ย้อนไม่ได้ · แก้ให้เล็กที่สุด
- บันทึกทุกการแก้ข้อมูลในไฟล์ 8 พร้อมบทเรียน 1–3 ข้อ · งานที่ย้อนไม่ได้ต้องถามก่อน · เว็บปฏิเสธบอทให้หยุด
ตอบเป็นภาษาไทย กระชับ อ่านบนมือถือได้
```

### 4.2 แม่แบบสั่งงาน AI (5 ส่วน)

```
เป้าหมาย: …
เสร็จเมื่อ: … (ตัดสินได้ว่าผ่าน/ไม่ผ่าน)
หลักฐานที่อยากเห็น: …
สิ่งที่รู้แล้ว: …
ข้อจำกัด: …
```

ตัวอย่าง:
- **ทำรายการซื้อ:** "ทำรายการซื้อชุดแรกแนว Sauvage · เสร็จเมื่อทุกรหัสอยู่ในไฟล์ 7 และไม่ติด ⓧ และสูตรตั้งต้นผ่าน IFRA ที่ 15% · หลักฐาน: ตารางรหัส + ลิงก์ + ตาราง IFRA · รู้แล้ว: งบราว 2,000 บาท · ข้อจำกัด: ไม่ต้องแก้ไฟล์ 1–7"
- **วิจัยเพิ่ม:** "เจาะลึก Armani Code แบบเดียวกับไฟล์ 2 · เสร็จเมื่อทุกข้อมีป้ายระดับหลักฐานและลิงก์ที่เปิดได้ · ข้อจำกัด: เพิ่มในไฟล์ 2 เท่านั้น"
- **โจทย์ยังไม่ชัด:** "อ่านข้อความนี้ แล้วสรุปปัญหาด้วยคำของคุณก่อน ยังไม่ต้องแก้อะไร"
- **แก้ทิศกลางทาง:** เอ่ยชื่อหลักหรือเลขกติกาแทนการอธิบายยาว เช่น "Prove It Works" หรือ "ผิดกติกาข้อ 2"

### 4.4 สกิล perfume-mode (ทางเข้าหลักแบบ poteto-mode)

- สกิลในบัญชี claude.ai ของผู้ใช้ (บันทึก 17 ต.ค. 2026) ไม่ได้เป็นเอกสารใน Project · Project instructions บรรทัดที่ 2 สั่งให้ทุกแชทโหลดสกิลนี้ก่อนเริ่มงานที่ไม่ใช่คำถามสั้น [โปรเจกต์นี้]
- ดัดแปลงจาก `/poteto-mode` ของ pstack: เลือก playbook → คัดลอกขั้นลง task list → ทำตามขั้น → พิสูจน์ผล → บันทึกบทเรียนในไฟล์ 8 [ต้นฉบับ: README ของ pstack]
- 6 playbook: (1) หาวัตถุดิบ/ทำรายการซื้อ · (2) ทำหรือปรับสูตร · (3) บันทึกผลดม · (4) แก้เอกสาร · (5) วิจัยหรือตอบคำถามความรู้ · (6) งานที่ไม่เข้าแบบไหน
- หลักที่ใช้ทุก playbook เป็นกติกาข้อ 1–7, 12, 14–15 แบบย่อ · ถ้าสกิลกับส่วน 4 ขัดกัน ให้ถือส่วน 4 เป็นหลัก แล้วเสนอแก้สกิลให้ตรง
- ข้อจำกัด: สกิลเป็นกฎแบบข้อความ ซึ่งบังคับได้อ่อนที่สุดตาม 2.4 — แชทอาจข้ามได้ ตัวที่ล้มได้จริงยังเป็น MSR verify (3.2) · AI แก้ไฟล์สกิลเองไม่ได้ ต้องเสนอฉบับใหม่ให้ผู้ใช้กดบันทึก
- ใช้ครั้งแรก 17 ต.ค.: แชท Claude Code โหลดสกิลแล้วใช้ playbook 4 แก้ไฟล์นี้ (ไฟล์ 8 ส่วน 11)
